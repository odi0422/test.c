1. 실험 결과

100개의 숫자를 랜덤으로 생성해서 배열과 BST에 저장한 다음, 50개의 숫자를 탐색해 보았다.

실행 결과 BST를 만드는 과정에서 총 612번의 비교가 발생했다.

50개의 숫자를 탐색했을 때는 다음과 같은 결과가 나왔다.

순차 탐색: 총 4,875회, 평균 97.5회
BST 탐색: 총 370회, 평균 7.4회
BST 생성 + 탐색: 982회

2. 결과 분석

두 방법의 결과를 비교해 보니 BST를 이용했을 때 비교 횟수가 확실히 적었다.

순차 탐색은 배열의 앞에서부터 하나씩 찾아가기 때문에 원하는 숫자가 없으면 100개의 숫자를 전부 확인해야 했다. 실제 결과에서도 대부분의 탐색 대상이 배열에 없었기 때문에 100번씩 비교하는 경우가 많았고, 평균 비교 횟수가 97.5회까지 올라갔다.

반대로 BST는 현재 숫자와 탐색할 숫자를 비교한 뒤 왼쪽이나 오른쪽 중 한쪽으로만 이동하기 때문에 모든 숫자를 확인할 필요가 없었다. 이번 실행에서는 평균 7.4번 정도만 비교하면 됐기 때문에 순차 탐색과 차이가 꽤 크게 나타났다.

처음에는 BST를 만드는 과정에서도 비교가 필요하기 때문에 순차 탐색보다 무조건 좋은 것은 아닐 수도 있다고 생각했다.

실제로 BST를 만드는 데 612번의 비교가 발생했다. 여기에 50번의 탐색에서 발생한 370번을 더하면 총 982번이다.

그래도 순차 탐색의 총 비교 횟수인 4,875번과 비교하면 BST 쪽이 훨씬 적었다. 따라서 이번 실험처럼 같은 데이터를 여러 번 찾아야 하는 경우에는 처음에 트리를 만드는 비용이 있더라도 BST를 사용하는 것이 더 효율적이라고 볼 수 있었다.

이번 실험에서는 BST의 탐색 비교 횟수가 평균 7.4회로 나왔지만, 항상 이렇게 나오는 것은 아닐 것 같다.

BST에 숫자가 들어가는 순서에 따라 트리의 모양이 달라지기 때문이다. 숫자가 어느 정도 골고루 나뉘어서 들어가면 탐색할 때 한쪽을 계속 제외할 수 있어서 빠르게 찾을 수 있다.

반대로 숫자가 비슷한 방향으로 계속 들어가면 트리가 한쪽으로 길게 늘어질 수 있다. 이렇게 되면 BST라고 해도 여러 노드를 계속 확인해야 해서 탐색 속도가 느려질 수 있다.

이번 실험에서는 BST 탐색이 순차 탐색보다 훨씬 적은 비교 횟수로 탐색할 수 있었다. 특히 BST를 만드는 데 필요한 비교 횟수까지 포함해도 982회로, 순차 탐색의 4,875회보다 적었다.

따라서 같은 데이터를 한 번만 찾는 것이 아니라 여러 번 찾아야 한다면 처음에 조금 시간이 걸리더라도 BST를 만들어 사용하는 것이 더 효율적이라고 생각한다. 다만 BST의 모양이 한쪽으로 치우치면 장점이 줄어들 수 있기 때문에 데이터를 어떤 순서로 넣는지도 중요하다는 것을 알 수 있었다.
